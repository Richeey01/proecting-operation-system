
# Практическая работа №6
## Синхронизация потоков — вариант B

### Цель работы
Изучить синхронизацию потоков, работу семафоров, блокировок и условных переменных, а также научиться обнаруживать и исправлять гонки данных.

### Используемые средства
- Python 3
- threading
- Semaphore
- Lock
- Condition
- Event

Внешние библиотеки не требуются.

### 1. Производитель–потребитель с семафорами
Файл: `producer_semaphore.py`

Реализован циклический буфер вместимостью 5 элементов, 3 производителя и 2 потребителя. Всего производится 1000 элементов.

- `empty_slots` считает свободные места.
- `filled_slots` считает занятые места.
- `mutex` защищает буфер от одновременного изменения.

Результат проверки:
- Ожидалось элементов: 1000.
- Обработано элементов: 1000.
- Все элементы уникальны: True.
- Потерь нет: True.

### 2. Производитель–потребитель с условной переменной
Файл: `producer_condition.py`

Используются циклический буфер вместимостью 5 элементов и `threading.Condition`.

Производитель ожидает, если буфер заполнен, а потребитель — если буфер пуст. После изменения состояния буфера вызывается `notify_all()`.

Результат проверки:
- Ожидалось элементов: 1000.
- Обработано элементов: 1000.
- Все элементы уникальны: True.
- Потерь нет: True.
- Нарушения: [].

### 3. Барьер для четырёх потоков
Файл: `barrier_demo.py`

Реализован барьер на основе условной переменной для 4 потоков и 3 фаз.

Поток не может перейти к следующей фазе, пока остальные потоки не достигнут барьера текущей фазы. Для повторного использования барьера применяется счётчик поколений.

Результат: все четыре потока прошли три фазы.

### 4. Потерянное уведомление
Файл: `lost_wakeup.py`

Программа намеренно демонстрирует ошибку синхронизации: поток проверяет условие без блокировки, а уведомление отправляется до начала ожидания.

В результате уведомление теряется, и поток завершает ожидание по тайм-ауту.

Правильный подход — проверять условие под одной блокировкой с ожиданием и использовать `while` для повторной проверки условия.

### 5. Гонка данных
Файл: `race_condition.py`

Четыре потока увеличивают общий счётчик по 100000 раз без блокировки.

Результат одного запуска:
- Ожидаемый результат: 400000.
- Фактический результат: 100400.
- Потерянные увеличения: 299600.

Причина — несколько потоков могут прочитать одно значение счётчика и перезаписать результаты друг друга.

### 6. Исправление гонки данных
Файл: `race_fixed.py`

Используется `threading.Lock`. Изменение общего счётчика выполняется под блокировкой.

Результат проверки:
- Ожидаемый результат: 400000.
- Фактический результат: 400000.
- Результат правильный: True.

### Контрольные вопросы

**1. Чем семафор со значением 1 отличается от мьютекса на практике?**

Семафор со значением 1 разрешает только одному потоку одновременно получить разрешение. Мьютекс предназначен для взаимного исключения и обычно связан с владельцем, который его захватил. Семафор также можно использовать для ограничения количества доступных ресурсов, а мьютекс — для защиты критической секции.

**2. Почему условную переменную нельзя использовать без мьютекса?**

Без мьютекса проверка условия и переход к ожиданию не защищены от вмешательства других потоков. Уведомление может прийти между проверкой условия и началом ожидания, из-за чего поток пропустит его. Мьютекс позволяет согласованно проверять состояние и ждать уведомления.

В ходе работы реализованы два варианта производитель–потребитель, циклический барьер, демонстрация потерянного уведомления и две версии программы со счётчиком. Проверки показали корректную обработку 1000 элементов и правильную работу блокировки при увеличении общего счётчика.
